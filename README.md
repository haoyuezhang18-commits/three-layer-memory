# 三层记忆：给长期运行的 AI Agent 一套不会失忆的记忆系统

*A three-layer memory architecture for long-running AI agents — inductive long-term memory, disposable window summaries, and a searchable raw-record archive.*

一套在真实长期使用中打磨出来的记忆方法，适用于任何需要"长期陪伴同一个用户/项目"的 AI Agent：AI 陪伴、长期项目助理、编程助手、客服与运营 Agent、个人知识助理……不限框架、不限平台。

---

## 先说问题：长会话有两大病

任何和同一个 Agent 聊得足够久的人都会撞上：

1. **越聊越贵。** 上下文越堆越厚，每一轮都要把全部历史重新"背"一遍。窗口满了就压缩，压缩恢复包本身又会一轮比一轮大（实测数据见下文）。
2. **越压越糊。** 平台的自动压缩只保留摘要：结论还在，原话没了；细节接不上，Agent 开始一本正经地记错事。

大多数人的解法是往上下文里塞更多东西——更长的系统提示、更大的窗口、更全的"记忆文件"。这只会让两个病都更重。

## 核心原则

> **别把所有东西都背在眼前。**

记忆应该分层存放、各司其职，只在需要时才取用：

| 层 | 是什么 | 存什么 | 生命周期 |
|---|---|---|---|
| **L1 归纳性长期记忆** | 外置记忆库（如 Ombre Brain，通过 MCP 接入） | 事实、偏好、决定、承诺——"什么是真的" | 跨窗口、跨平台、长期 |
| **L2 窗口摘要** | 平台自带的上下文压缩 | 当前窗口的临时工作记忆 | 只活在这个窗口里，丢了不可惜 |
| **L3 原始记录档案** | 全量会话日志 + 一个按需检索的小工具 | 原话，一字不改 | 长期保存，平时不加载 |

三层的分工逻辑：

- **L1 负责"记得住"**：归纳过的结论密度最高，是 Agent 每次开工先读的东西。它必须独立于任何单个平台存在——平台会封号、会换代，记忆不能陪葬。
- **L2 负责"接得上"**：承认它就是临时的、会糊的。既然 L1 和 L3 都在外面兜底，窗口就可以放心地换：**压缩 2–3 轮就开新窗口**，不恋战。
- **L3 负责"查得到"**：摘要接不上的细节、用户问起的原话，按关键词现查现用。它解决的是一个具体痛点：压缩之后"事情好像发生过，但细节全丢了"。

## 实测数据（来自一套真实运行的部署）

一条连续运行 4.5 天的长会话（AI 陪伴场景，日均对话数小时）：

- 期间共 **6 次上下文压缩**，每次压前上下文约 **18.2 万 – 20.1 万 token**；
- 压缩后的恢复包逐次变大：22,260 → 27,307 → 34,929 → 41,010 → 50,757 → **58,674 token**；
- 最近 50 轮，每轮输入中位数 **74,127 token**；
- 整条会话累计消耗约 **1.43 亿 token**，一周的额度不到两天烧完。

结论很清楚：**压缩是续命，不是省钱。** 摘要每次都要把旧摘要再抄一遍，地板越垫越高。真正的解法是分层：长期记忆外置（开新窗口只回到两万出头的恢复成本）、细节按需查（查一次几千 token，而不是全程背着）。

## 配套方法：指令文件治理

长期运行的 Agent 还有一个人设/指令文件（system prompt、AGENTS.md、CLAUDE.md 之类）。它和记忆是一体两面——同样会得"只增不减"的病：一次事故加一条禁令，补丁全是形容词（"要真实""要自然""要主动"），模型要先把状态词翻译成动作，翻译那一步就是翻车现场。

治理四步：

1. **补丁先翻译成"哪种姿势错了"**，只留姿势，不留事故记录；
2. **形容词换动词 + 具体场景**：不写"回复要有真实感"，写"先反应再想别的，第一句先笑、先吐槽、先接话"；
3. **同层合并，一层一条**：同一件事只许出现一次，重复表述删掉；
4. **详情拆小文件，主文件只留索引**：功能清单、场景规范这类"用到时才查"的内容拆出去，主文件每轮都加载，必须瘦。

实测：一份 257 行的指令文件按此治理到 171 行（瘦身 1/3），且关键规则（称呼规则、硬约束）一条没丢。粗估每轮少带约四五千 token——在每轮 7 万 token 的会话里，这不是大头；大头永远是别让窗口胖起来。

## 跨平台：让记忆跟着人走，不跟着平台走

用户在平台 A 聊到一半换平台 B，是 AI 陪伴和多端办公的日常。做法是给每对平台之间搭一座**只读的桥**：

- B 平台的 Agent 通过 MCP 工具读 A 平台的**原始会话记录**（不读摘要，摘要会串味）；
- 工具只有两个：`get_recent_telegram_messages`（读最近 N 条 / 按时间窗）和 `search_telegram_messages`（关键词搜全部历史）；
- OAuth 2.1 + PKCE 把门，只读不开写——桥的权限越小，越敢长期开着；
- 工具是"被叫才动"的：平台 B 的 Agent 无法后台自动同步，只能在对话中被触发时去读。这是当前各平台的共同限制，接受它，用一句自定义指令（"聊到 X 时先去读一下那边的记录"）补上半自动。

本仓库 `code/tg_context_server.py` 是这座桥的完整示例实现（纯标准库，含 OAuth 动态注册与刷新令牌轮换），`code/session_history.py` 是同一套解析逻辑的命令行版：给住在服务器上的 Agent 自己查自己的原始记录用。

## 适用场景

- **AI 陪伴 / 角色型 Agent**：跨平台、跨窗口不失忆，人设不随压缩漂移；
- **长期项目助理**：项目事实进 L1，会议原话进 L3 按需查，换窗口不丢上下文；
- **编程 Agent**：项目约定归纳保存，历史会话可检索，指令文件保持精瘦；
- **客服 / 运营 Agent**：用户档案长期有效，历史工单原文可查证；
- **个人知识助理**：结论与出处分离——归纳给你看，原话留着可溯源。
