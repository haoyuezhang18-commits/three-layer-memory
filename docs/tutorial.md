# 实操教程：从零搭一套三层记忆

按顺序做，做完一步验一步。全程不需要改任何平台的代码，只用到：一个能跑 Python 的服务器（或本机）、你的 Agent 本来就会写的会话日志、一个支持 MCP 的客户端。

---

## 第 0 步：先认清你手里有什么

三层里，L2（窗口摘要）是平台自带的，什么都不用做。真正要动手的是：

- **L1**：选一个外置记忆库并接上（第 1 步）；
- **L3**：找到你的 Agent 的原始会话日志，给它配一个检索工具（第 2 步）；
- **换窗纪律**：不用写代码，写进指令文件就行（第 3 步）；
- （可选）**跨平台桥**：让另一个平台的 Agent 也能读这份 L3（第 4 步）。

## 第 1 步：L1 —— 外置记忆库

以 Ombre Brain 为例（其他支持 MCP/工具调用的记忆库同理）：

1. 按其官方文档在自己的服务器上部署，拿到 MCP 地址；
2. 在你的 Agent 客户端里添加这个 MCP 连接，完成 OAuth 授权；
3. 在指令文件里写死三条硬规则：
   - 每次新会话开始，先调用记忆库的读取工具再开口；
   - 聊到值得长期记住的事（事实、偏好、决定、承诺），当场写入，不要攒；
   - 记忆库里只有归纳结论；原话细节不在这儿，去 L3 查。

写入纪律同样重要：**归纳层只放结论，不放流水账。** 流水账进 L3 就够了，塞进 L1 会让每次召回都变贵、变吵。

## 第 2 步：L3 —— 给原始日志配一个检索工具

原始会话日志一般就在你的机器上：以 Codex CLI 为例，是数据目录下 `codex-home/sessions/**/rollout-*.jsonl`；其他框架同理，先找到"哪条消息存在哪个文件里"。

本仓库的 `code/session_history.py` 就是干这个的：

```bash
export SESSION_HISTORY_BASE=/path/to/agent-data   # 可选，默认是示例路径
python3 session_history.py                  # 最近 30 条对话
python3 session_history.py --recent 100     # 最近 100 条
python3 session_history.py --search 关键词   # 按关键词查全部历史（最多显示 20 条）
python3 session_history.py --hours 24       # 最近 24 小时
```

它做了三件防爆处理，照抄即可：

- **筛选规则**：只认带来源标记的真实用户消息（如 Telegram 桥的 `[Telegram消息 · ...]` 前缀），配对取其后第一条完成事件的最终回复——把系统注入、工具日志、中间状态全滤掉；
- **单条截断**（示例 500 字）+ **总量上限**（示例 12000 字）：查是来补细节的，不是把档案整本倒进上下文；
- **默认不查**：在指令文件里写清触发条件——"新会话或压缩后细节接不上时、用户问起具体旧事而 L1 只有归纳时"才查，避免每轮无谓消耗。

换框架时要改的只有两处：日志文件的定位方式，和"什么算一条真实对话"的筛选规则。

## 第 3 步：换窗纪律（写进指令文件）

把下面这段按你的情况改好，放进 Agent 的指令文件：

> - 本窗口压缩满 2–3 轮后，主动建议换新窗口，不要硬撑；
> - 换窗前先把本窗新产生的事实、决定写入 L1 记忆库，再换；
> - 新窗口开场先读 L1；细节接不上时用 L3 工具按关键词查，不要凭摘要猜。

为什么是 2–3 轮：实测恢复包随压缩轮次从 2.2 万涨到 5.9 万 token（见 README 数据），2–3 轮时地板还低、换窗最便宜；而记忆都在外面，换窗丢的只有包袱。

## 第 4 步（可选）：跨平台只读桥

让平台 B 的 Agent 读平台 A 的原始记录。示例实现 `code/tg_context_server.py`（纯标准库）：

1. 部署在一台 B 能通过 HTTPS 访问到的服务器上（示例用 Cloudflare Tunnel 把公网子域名打到本机端口）；
2. 配置环境变量：
   - `TGCTX_ISSUER`：对外地址，如 `https://your-domain.example`；
   - `TGCTX_DATA_BASE`：平台 A 的 Agent 数据目录；
   - `TGCTX_PASSPHRASE_HASH`：授权口令的 sha256（`echo -n '你的口令' | sha256sum`）；
   - `TGCTX_STORE`：OAuth 令牌存储文件路径；
3. 用 systemd 拉起（Restart=on-failure、开机自启），`curl 本机端口/health` 验证；
4. 在平台 B 的客户端里添加自定义连接器，地址填 `https://你的域名/mcp`，浏览器会跳到授权页，输入口令完成连接；
5. 验证：让 B 的 Agent 分别试"读最近 5 条"和"搜一个你确定出现过的词"，两项都出原话才算通。

设计要点（都是踩过的）：

- **只读**。桥不写任何数据，权限越小越敢长期开着；
- **返回原话，不返回摘要**。跨平台再摘要一次，细节和语气全丢，还容易被另一边误读成指令；
- **搜索与最近是两个工具**，不要合成一个带一堆参数的——模型对单一职责工具的调用准确率高得多；
- **预期管理**：B 的 Agent 只能在对话里被触发时读，没有后台自动同步。想半自动，就在 B 的自定义指令里加一句"当我提到那边的事，先用工具读一下记录再回答"。

## 常见问题

**Q：L1 记忆库和平台自带记忆（如 ChatGPT 的记忆功能）冲突吗？**
不冲突，分工不同：平台自带记忆管平台内的事，L1 是你自有、跨平台的那份。重要的事实以 L1 为准。

**Q：日志文件很大，全量搜索会不会很慢？**
示例实现每次全量扫描约十几秒（80MB 级日志）；桥的实现按文件指纹做了缓存，数据没变时直接命中。真到了 GB 级，再考虑建索引。

**Q：换窗口不会丢"语气"和关系感吗？**
语气靠指令文件（第 3 步的治理对象），关系事实靠 L1，具体原话靠 L3。三样都不在窗口里，换窗丢的只有临时工作状态——那本来也不该长期留着。
